## 题目

上一道题（B1）产出了文档差异表。这一题把它变成**能执行的计划**。

输入：目标版本（`18.0` 或 `20.0`）。
输出：一份 `plan.json`，由一个"笨执行器"顺序跑完。

**你不执行安装，只生成计划。** 我们提供执行器。

## 交付

`plan.json`：

```json
{
  "version": "18.0",
  "steps": [
    {
      "id": "apt-update",
      "desc": "更新包索引",
      "command": "apt-get update",
      "expect": "Reading package lists",
      "on_fail": "retry:3"
    },
    {
      "id": "python",
      "desc": "确认 Python 版本满足要求",
      "command": "python3 --version",
      "expect": "3\\.(1[0-9]|[2-9][0-9])",
      "on_fail": "abort"
    }
  ]
}
```

字段约定：

| 字段 | 含义 |
| --- | --- |
| `command` | 一条 shell 命令，非交互 |
| `expect` | 执行后 stdout+stderr 里必须能匹配到的字符串或正则 |
| `on_fail` | `abort`（停止）或 `retry:N`（重试 N 次） |

## 验收

我们提供一个 `executor.sh`，在干净的 `ubuntu:24.04` 里按顺序执行你的计划：

- 每一步的 `expect` 必须命中，否则该步判失败
- 全部步骤走完，退出码 0
- 执行完后 Odoo 能起来

**计划里可以写探测逻辑**（比如先查版本再决定装哪个包），但不能把 B1 的结论直接抄成一堆 `apt install` —— 我们要看的是"计划"，不是"命令清单"。

## 评审标准

| 维度 | 权重 | 看什么 |
| --- | --- | --- |
| 可执行性 | 50% | 在干净容器里能不能跑到底 |
| 失败判据 | 30% | `expect` 写得够不够严，能不能真的发现问题 |
| 可读性 | 20% | 每步的 `desc` 是不是说清楚了在干什么 |

## 规则

- 参与者须为在校学生（计算机 / 数学 / 统计 / 经济等相关专业），报名时确认
- 计划必须是数据（JSON），不能是脚本；执行器是唯一的执行者
- 每人限交一份，截止前可以改
